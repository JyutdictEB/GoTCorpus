# 🔴 高

## SEO-01　hash 路由导致内容对搜索引擎不可见

- **现象**：全站路由为 `#/vocabulary` 形式。
- **证据**：`quasar.config.js` 中 `vueRouterMode: 'hash'`；`src/router/routes.ts:8-14`。
  Google Search Central《网址结构最佳实践》原文：
  > 请勿使用网址片段更改内容 —— 请勿使用片段更改网页内容，因为 Google 搜索通常不支持网址片段。以下是网址片段示例：`https://example.com/#/potatoes`。如果您要使用 JavaScript 更改内容，请改为使用 History API。
  来源：https://developers.google.com/search/docs/crawling-indexing/url-structure
- **影响**：7 个页面在搜索引擎眼中只是 1 个 URL，即首页。
- **建议**：改用 history 模式（方案 B 第 1 步）。

## SEO-02　非 hash 路径全部 404，且部署配置不在仓库

- **现象**：`/vocabulary`、`/introduction`、`/about` 均返回 404。
- **证据**：线上实测 `curl -o /dev/null -w "%{http_code}"` → 404 / 404 / 404。
- **影响**：一旦切换到 history 模式而忘记加 SPA fallback，整站立刻全挂。
- **建议**：加 `public/_redirects`（内容 `/*  /index.html  200`），并把托管配置纳入版本控制（见 ENG-02）。

## SEO-03　无 per-locale URL、无 hreflang

- **现象**：语言（en-US / zh-HK）只存在 localStorage，不体现在 URL 上。
- **证据**：`src/boot/i18n.ts` 的 `STORAGE_KEY = 'locale'`；全站无 hreflang。
- **影响**：zh-HK 的全部内容对爬虫不存在；两种语言无法各自被检索。
- **建议**：若短期不做，至少在方案 B 的预渲染中把当次渲染的 `lang` 固化进 HTML。

## SEO-04　title / description 全站相同且从不更新

- **现象**：所有页面的 `<title>` 都是 `Lagarrue's GoT Cantonese Online Corpus`。
- **证据**：全仓库搜索不到 `useMeta` / `document.title`；`dist/spa/index.html` 中 title 与 `meta description` 内容完全一致，且 description 等于产品名。
- **影响**：搜索结果里 7 个页面长得一模一样，description 无信息量。
- **建议**：启用 Quasar `Meta` 插件，每个页面 `useMeta()`。

## SEO-05　无 sitemap.xml；robots.txt 为托管商默认

- **现象**：`/sitemap.xml` 返回 404；`/robots.txt` 是 Netlify 默认的 content-signals 模板，无 `Sitemap:` 指令。
- **证据**：线上实测；仓库 `public/` 下只有 favicon 与 icons。
- **建议**：方案 B 的预渲染脚本顺带生成 sitemap；在 `public/robots.txt` 里声明。

## SEO-06　全站无 `<h1>`，`<html>` 无 `lang`

- **现象**：页面主标题用 div 而非语义标题；html 根元素无语言声明。
- **证据**：`src/pages/AboutPage.vue:3` 为 `<div class="text-h5">`；`index.html:2` 为裸 `<html>`；其余页面标题来自 `q-table` 的 `title` 属性（渲染为 div）。
- **影响**：搜索引擎与辅助技术都拿不到页面层级结构；语言定向缺失。
- **建议**：主标题改 `<h1>`，`<html lang>` 随 locale 切换。

## DATA-01　机翻条目质量不达标

- **现象**：词表法/越两列 Google 译文存在系统性错误。
- **证据**（实测计数）：
  | 指标 | 法语列 | 越南语列 |
  |---|---|---|
  | 译文非空 | 2416（原文 2455，漏译 39） | 2178（原文 2203，漏译 48） |
  | 译文仍残留拉丁字母 | 84（3.5%） | 89（4.1%） |
  | 译文与「对应汉字」完全相同 | 217 / 2416（9%） | 154 / 2178（7%） |

  2 174 条同时有法、越两列译文，其中 **1 538 条（70.7%）三个字段（法译、越译、汉字）互不相同**。

  具体错误样本：

  | 原文 | Google 输出 | 问题 |
  |---|---|---|
  | `un` | `A` | 应为「一」，输出成字母 |
  | `mur en pisé` | `Adobe Wall` | 输出了**英文** |
  | `depouiller` | `壓抑` | 应为「剝皮」，取错义项 |
  | `sampan, bateau` | `Sampan，船` | 半译半留 |
  | `toiture de tuile` | `tuile屋頂` | 中法混排 |
  | `tử tế` | `種類` | 应为「客氣／得體」 |
  | `belle-mère (m. de lamme)` | `婆婆（M。DeLamme）` | **源文本本身是 OCR 垃圾**，模型硬凑 |
- **影响**：这两列是目前词表的主要中文释义来源，错误会直接传播给使用者。
- **建议**：见「既定方向」——新增 LLM 列，并**保留原列**不覆盖，以维持数据溯源。

## DATA-02　人工校订率与对外表述有张力

- **现象**：`French (Trans. Corr.)` 仅 215 / 2490 条非空（8.6%）；`Vietnamese (Trans. Corr.)` 仅 172 / 2490 条（6.9%）。
- **证据**：字段填充率实测。且这 215 / 172 条中，与 Google 输出**完全一致**的只有 12 条（5.6%）和 9 条（5.2%）——校订者几乎全部做了改动。
  > 注：「不一致」包含措辞规范化（校订列明显是词典体，如 `adv. 合适地,适当地…`），
  > 因此 94% 是**错误率的上界**，不等于 94% 全错。
- **对照**：`src/i18n/en-US/index.ts:78` 对外表述为 French/Vietnamese annotations "were machine-translated in batches and **checked by hand**"。
- **影响**：公开发布时的表述与实物不符，属于学术诚信风险。
- **建议**：发布前二选一——补足校订，或修正 About 页措辞并明确标注校订覆盖范围。

## DATA-03　数据无法导出

- **现象**：全站没有任何 CSV / JSON 下载入口。
- **证据**：7 个页面组件中无下载链接；`src/i18n/en-US/index.ts:84` 称数据库 "will be open-sourced after further proofreading"。
- **影响**：研究者无法本地检索、无法复现、无法二次利用；语料库的核心价值被限制在网页表格里。
- **建议**：提供按 section 的 CSV/JSON 导出（可与「进一步校订」解耦，先标为 provisional）。

## DATA-04　无条目级 permalink

- **现象**：无法生成指向某一条词条 / 例句 / 成语的链接。
- **证据**：`src/router/routes.ts` 只有 7 条路由；表格分页且无 URI 同步。
- **影响**：学术写作无法按条引用（"見語料庫第 1234 號"）；也无法分享具体词条。
- **决定**：2026-10-11 **明确不做**条目级 URL，接受此限制，改用「表格全量渲染 + 页内锚点」缓解。

# 🟡 中

## DATA-05　`*` 与 `□` 约定无图例

- **现象**：`Corres. Char.` 列中 177 条以 `*` 开头（如 `*摏牆`），40 条含 `□`（如 `□□`、`□房`、`谷□`）。
- **影响**：使用者无法判断这是"推測字形""待考"还是其他含义。
- **建议**：加图例（表格下方或 About 页）。

## DATA-06　越南语原文字段缺失 287 条

- **现象**：`Original Vietnamese Text` 非空 2 203 / 2 490。
- **影响**：这 287 条的越语译列必然为空；使用者也看不出是"原书没有"还是"未录入"。
- **建议**：区分「原书无此项」与「未录入」两种状态。

## DATA-07　Note 字段自由文本、语言混杂

- **现象**：199 条非空，内容形如 `可能有gvun`、`交帶`、`越粵音`、`昨暮日？`、`原書聲調標錯？`。
- **影响**：无法筛选、无法统计，疑问句与断言混在同一列。
- **建议**：拆出「标记类型」维度，或在 About 页说明 Note 的写法惯例。

## DATA-08　introduction.json 仍有 OCR 残留

- **现象**：第 1 条原文写作 `un palois`、`la prélention`、`le «canionais»`。
- **应为**：`patois` / `prétention` / `cantonais`。
- **对照**：`src/i18n/en-US/index.ts:78` 声明 "The French parts were processed with OCR (Azure AI Vision) and then **manually corrected**"。
- **影响**：与 DATA-02 同类——表述与实物不符；也说明任何自动化再处理都必须配验证门禁。

## DATA-09　无版本号 / DOI / 数据快照标识

- **现象**：界面显示 v0.1.0（软件版本），但数据本身没有版本或内容哈希。
- **影响**：引用时无法定位到具体的数据状态。
- **建议**：数据加语义化版本或内容哈希，随导出与页面一并展示。

## UI-01　不探测浏览器语言

- **现象**：首次访问一律英文。
- **证据**：`src/boot/i18n.ts` 的 `resolveInitialLocale()` 在无 localStorage 时固定返回 `'en-US'`，未读取 `navigator.language`。
- **影响**：粤语语料库的中文用户首访看到英文界面。
- **建议**：回退顺序改为 localStorage → navigator.language → en-US。

## UI-02　`row-key="name"` 指向不存在的字段

- **现象**：`src/pages/VocabularyPage.vue:5` 使用 `row-key="name"`，但 vocabulary.json 无 `name` 字段。
- **影响**：所有行 key 均为 `undefined`，分页 / 筛选切换时可能出现 DOM 复用错位。
- **建议**：改为 `row-key="Index"`（Index 在各文件内唯一，1..N，已实测无重复）。

## UI-03　图片无尺寸属性、未 WebP 化

- **现象**：三张扫描件通过 `q-img` 引用（`src/pages/IndexPage.vue:13,19,25`），无 width/height/ratio，最大 158 KB。
- **影响**：布局偏移（CLS）；移动端加载浪费。
- **建议**：加 `:ratio` 或尺寸属性；生成 WebP 并降采样。

## UI-04　viewport 禁止缩放

- **现象**：`index.html:10` 为 `user-scalable=no, maximum-scale=1`。
- **影响**：违反 WCAG 1.4.4，低视力用户无法放大页面。
- **建议**：移除 `user-scalable=no` 与 `maximum-scale`。

## UI-05　`my-sticky-header-table` 是一个从未定义的类

- **现象**：5 个表格页面都写了 `class="my-sticky-header-table"`（`src/pages/VocabularyPage.vue:4`、SentencesPage、IdiomsPage、IntroductionPage、PhonemeDescriptionPage 均为第 4 行），但该 class 在全仓库**没有任何定义**。
- **证据**：`src/css/app.scss` 全文只有一行注释；`grep -rn "sticky" src/css/` 无结果。
- **影响**：表头吸顶（被设想过的功能）实际不生效。全量渲染后页面高度约 90,780 px，**滚动时表头丢失**会从"小事"升级为影响可用性问题。
- **建议**：要么补上样式（滚动容器 + `thead th { position: sticky; top: 0 }`），要么删掉这个类名。

## ENG-01　vocabulary chunk 876 KB，而默认只显示 5 行

- **现象**：`dist/spa/assets/vocabulary-*.js` 达 876 KB；`dist/spa` 总计 2.5 MB。
- **证据**：`quasar.config.js` 的 `chunkSizeWarningLimit = 1100` 已将告警压掉。
  **勘误（2026-10-11 复测）**：Vite 产出的并非 JS 对象字面量，而是在 JS 模块里包一层 `JSON.parse(...)`（形如 `var e=JSON.parse(...); export{e as default}`）。实测求值整块 6.0 ms vs `JSON.parse` 原文件 4.8 ms，**差额仅 1.2 ms，可忽略**。
  ⇒ 本条的问题在**下载量**，不在解析方式；不必为"改成 fetch JSON"而改架构。
- **影响**：为展示 5 行加载 876 KB；移动端首屏明显变慢。
- **建议**：配合方案 B 把默认每页改为「全部」后，这份数据从"白加载"变成"真的在用"，问题自然降级；
  至于改 `fetch` 拉取 `.json`，收益主要在 HTTP 缓存语义与可流式解析，**不在解析速度**，优先级低于本条其它工作。

## ENG-02　部署配置不在仓库

- **现象**：仓库无 `netlify.toml` / `_redirects` / `_headers`。
- **证据**：`git ls-files` 与根目录检查均无；线上由 Netlify Edge 提供（响应头含 `x-nf-request-id`、`cache-status: "Netlify Edge"`）。
- **影响**：部署不可复现；缓存与安全头不受版本控制；改路由模式时必须靠外部面板操作，易遗漏。
- **建议**：把托管配置收进仓库（方案 B 的前置条件）。

# 🟢 低

## ENG-03　无测试

- **现象**：`npm test` 是占位符（`echo "No test specified" && exit 0`）。
- **影响**：质量门禁只有 lint + build；数据格式或字段改名不会有任何测试报警。
- **建议**：先加数据 schema 校验（字段齐全、Index 唯一、必填列非空），成本低、收益直接。

## ENG-04　版本号硬编码在两处

- **现象**：`src/layouts/MainLayout.vue:29` 写死 `v0.1.0`，与 `package.json` 的 `version` 重复。
- **影响**：必然漂移（AGENTS.md 也已提示需手工保持同步）。
- **建议**：构建期注入（`import.meta.env` 或 Vite define）。

## ENG-05　无站点分析

- **现象**：无任何统计代码。
- **影响**：SEO 改造的效果无法度量，无法判断是否需要继续投入。
- **建议**：接入轻量、隐私友好的统计（如自建 Umami / Plausible），或先用 Search Console 的曝光数据兜底。

# 附录 B：关键实现约束（实测，方案 B / LLM 列都需要）

1. **隐藏列不参与搜索。** `node_modules/quasar/src/components/table/QTable.js:241-246` 把 `computedCols.value`（= 经 `visibleColumns` 过滤后的列）传给 `filterMethod`。

4. **Index 字段在各数据文件内唯一且连续**：vocabulary 1..2490、sentences 1..194、idioms 1..45、phoneme_description 1..77、introduction 1..34，均无重复。可作为 LLM 译文 overlay 的键。

| 全量 2,490 行 × 13 列 | 67,255 | 32,370 | 295 ms | 45 ms | 224 ms | 20 ms | 116,000 px |

**结论**：

1. **网络不是瓶颈，反而是收益。** 全量 7 列 HTML 893 KB 原始 / **brotli 69 KB**，比现在的 JS chunk（872 KB / **brotli 93 KB**）更小——重复的 class 名压缩率极高，传输量反而下降约 26%。
2. **解析不是瓶颈**（37 ms）。
3. **首次布局是主要成本**（131 ms）。桌面可接受；移动端按 3–4 倍估算约 0.4–0.5 s。
4. **真正的浪费是"画两遍"**：预渲染出的 DOM 会被 Vue 挂载时清空重建，额外 +130 ms。用真 hydration（Quasar SSR 模式）可完全消除——**这是方案 B 最需要处理的一环**。
5. **"搜索会卡"的担心不成立**：筛选从 2,490 行删到 50 行只需 11 ms，Vue 的 patch 不会与这个数量级有差异。
6. **默认收起 Google / DeepL 列在性能上也是对的**：13 列比 7 列多约 258 ms 解析 + 93 ms 重渲染。

**保真度说明**：未启用 CPU 节流；"整表重渲染"用 `innerHTML` 整块重建作为**上界**（Vue 用 DOM API 逐节点创建通常更快）；真实 q-table 的包裹层比测试页略多。

# 附录 G：方案 B 的官方实现路径 —— Quasar SSG Mode（2026-10-11 追查）

## 官方文档写明的三个必改点

1. **数据加载必须从 `onMounted` 移到 `preFetch`。**
   原文："Data used to create build-time metadata must be available while the page is rendered.
   If metadata is fetched only after hydration, it will not be present in the generated HTML."
   ⇒ 本仓库 5 个表格页面目前都在 `onMounted` 里 dynamic import JSON，构建期渲染出来会是**空表格**。

2. **语言状态存在 localStorage 会造成 hydration mismatch。**
   官方把 `$q.localStorage` / `$q.sessionStorage` 明确列入"hydration 前应避免"清单，
   并强调 "An SSG build therefore has no real browser request, cookies, user agent, viewport, or browser storage"。
   ⇒ `src/boot/i18n.ts` 的 `resolveInitialLocale()` 正读 localStorage：
   构建期渲染 en-US，回访的 zh-HK 用户首帧渲染 zh-HK → 不匹配。
   解法：改为 URL 前缀 / cookie，或用官方 `useHydration` composable 把语言相关渲染推迟到客户端。

3. **meta / title 必须用 Quasar Meta 插件在渲染期声明**，构建期才会写进 HTML（官方 "SEO for SSG" 章节明确要求）。
   官方同时说明：robots.txt 与 sitemap **不会**由 SSG 页面列表自动生成，需自行产出。

## 对既定方向的影响

- "不做条目级 URL"不受影响，仍成立。
- **但 per-locale URL 从"可选"变成"若不做的代价"**：SSG 是构建期渲染，单次构建只能固化为一种语言。
  不做 `/zh-HK/...` 前缀，zh-HK 内容就依然对搜索引擎不可见（对应 SEO-03）。
- 方案 B 的实现路线二选一：
  - **路线 1（官方，推荐）**：升级 `@quasar/app-vite@3` + `vue-router@5`，启用 SSG 模式。真 hydration，不重画。风险：大版本升级 + SSG 处于 beta。
  - **路线 2（保守）**：留在 v2.6.2，用 Playwright 构建期预渲染。无升级风险，代价是附录 F 里那 130 ms 重渲染 + 约 150 MB Chromium 依赖。

## 修订（2026-10-11，用户反馈后）

反馈的两个问题都成立，是我引入的设计缺陷：

**问题 1：嵌套滚动条 + 表头会滚走。**
第一版把表格包成 `.tablewrap { max-height: calc(100vh - 150px); overflow: auto }`，
于是页面本身还能滚、表格区也能滚 —— **两条滚动条并存**；而且页面一滚，表格区顶部连同粘性表头一起被推出视口，
表头就"消失"了（粘性定位的参照是滚动祖先，不是视口）。

> 根因：`position: sticky` 相对**最近的滚动祖先**定位。一旦某祖先有了 `overflow`（除 visible 外），
> 粘性就不再相对视口。这是"横向可滚 + 表头吸顶"两者天生冲突的原因，无法靠调参解决。

**修法：表格页改用应用外壳（app shell），全页只有一个滚动容器。**

\`\`\`css
html:has(body.shell), body.shell { height: 100%; }
body.shell { display: flex; flex-direction: column; overflow: hidden; height: 100dvh; }
body.shell main { flex: 1; min-height: 0; display: flex; }

### 顺带发现的坑：Astro 模板体里的 `\uXXXX` 转义

**根因**：

| 位置 | `\uXXXX` 会被解释吗 |
|---|---|
| frontmatter 的 JS 字符串（`const x = "\u00b7"`） | ✅ 会（JS 引擎解释） |

| 模板表达式内（`{a.b + " \u00b7 " + c}`） | ✅ 会（是 JS 表达式） |

## 修订五：首页改为「左文右图 + 自动轮播」（2026-10-11）

### 问题

### 改法

改为 hero 双栏：**左侧标题 + 概述，右侧自动切换的扫描图查看器**。

\`\`\`css
.hero {
  display: grid;
  grid-template-columns: minmax(0, 1fr) minmax(230px, 350px);
  gap: 64px;
  align-items: start;
}
\`\`\`

轮播实现：三张图绝对定位叠放，靠 `opacity` 交叉淡入（0.7s），5.2 秒自动切换一次。

配套行为：

- 鼠标悬停 / 键盘聚焦时**暂停**（`mouseenter` / `focusin`），离开恢复
- 标签页切到后台时停止计时（`visibilitychange`），避免无意义的重绘与偏移累积
- 遵循 `prefers-reduced-motion`：设为 reduce 时**不自动播放**，但仍可手动切换
- 圆点与左右按钮均可点，圆点带 `aria-current`，图注用 `sr-only` 保留在无障碍树里
- 容器用 `aspect-ratio: 621 / 912` 锁定高度，避免切换时布局跳动

\`\`\`

图片改为在上方留白、`contain` 自适应缩放 —— 缩放的留白是白底上的白边，视觉上不可见。

同时把轮播控制条**浮到图片上**（绝对定位 + 半透明胶囊底），省掉一整行高度，把空间让给图片。

改后实测（两种语言均）：

| | 英文 | 粵文 |
|---|---|---|
| hero 行高 | 526 | 422 |
| 左栏 / 右栏 | 522 / 522 | 418 / 418 |
| **两栏高度差** | **0** | **0** |
| 左栏底到区块顶 | 56 px（有意留的区块间距） | 56 px |

### 改这个时踩的坑

把控制条改成绝对定位后，它压到了图注上 —— 页面上显示成 `Co[按钮]ook`。

原因：`.plate-bar` 在 DOM 里是 `.plate-stage` 的**兄弟节点**，不是子节点，
所以 `position: absolute` 相对外层 `.plates` 定位，而不是相对舞台。
用 CDP 查 `offsetParent` 一下就看出来了（返回 `plates` 而非 `plate-stage`）。

修法：把控制条移进 `.plate-stage` 内部。移动后 `offsetParent` 变为 `plate-stage`，
控制条落在 573–611（舞台 140–622 内），图注在 632 下方，不再重叠。

> 教训：**给元素加 `position: absolute` 前，先确认它的父容器是谁** —— 直觉上的「里面」和 DOM 里的父子关系不一定一致。

### 修订五·五补：控制条不再叠在扫描件上

上一版为了省 38px 高度，把轮播控制条绝对定位叠在图片底部。用户当即指出：**遮住了扫描件的正文**。
这是对的 —— 扫描件本来就是给人读的，控制条压在上面等于把内容弄没了。省下的那点高度不值。

**修法：控制条回到文档流，但和图注并成一行。**

\`\`\`html
<div class="plate-stage"> …图片… </div>
<div class="plate-foot">
  <div class="plate-bar"> ‹ ●○○ › </div>
  <p class="plate-cap">Cover page of the book</p>
</div>
\`\`\`

\`\`\`css
.plate-foot { display: flex; align-items: center; gap: 16px; margin-top: 10px; }
.plate-bar  { flex: 0 0 auto; }
.plate-cap  { flex: 1 1 auto; min-width: 0; margin: 0; }
\`\`\`

这样既挡不住内容，也不额外占高度（控制条与图注同一行，合计 26px，比原本「图注 29 + 控制条 38 = 67px」还省 41px）。

实测（英文）：

| 元素 | 位置 |
|---|---|
| 舞台（图片） | 140 → 625 |
| 控制条 | 635 → 661（文档流，图片之外） |
| 图注 | 641 → 656（与控制条同一行） |
| 两栏高度差 | **0** |
| 左栏底到区块顶 | 56 px（有意的区块间距） |

> 一并解决了一个定位坑：`.plate-bar` 曾是 `.plate-stage` 的兄弟节点，
> 拿它做绝对定位会相对外层 `.plates` 定位 —— 这是上一版压住图注的直接原因。
> 现在它回到文档流，不再有此问题。

# 附录 L：LLM 译文列落地（2026-10-11/12）

## 一、范围决定：砍掉 96%

最初方案是全量翻译 2,840 条 × 2 语言 = 5,680 条。执行前做了两轮收缩：

**第一轮：只用一列，且只翻法语。** 用户明确「翻译主要是给不会法语的人看原文，所以不是各一条，只是翻译法语而已」。
越南语那几列是原书并列的注（多为汉字对应的汉越音，如 `thiù`→條、`phắt`→匹），与汉字列高度重合，不是翻译对象。

**第二轮：只翻没有汉字对照的。** 用户追问「这些词条真的有必要翻译吗，我觉得只有必要翻译那些大段的」。
实测证实：词表里 **60% 的翻译输出⊆汉字**，即 `門→門`、`燈→燈`、`遠→遠`，纯属把汉字列抄一遍。

最终规则：**汉字列已经是答案的，不翻。**

| 数据集 | 有汉字列？ | 结论 |
|---|---|---|
| vocabulary | ✅ 對應漢字 | 不翻 |
| sentences | ✅ 去 邊處 ？ | 不翻 |
| idioms | ✅ 惡者 惡報… | 不翻 |
| **introduction** | ❌ 纯法语长文 | **翻** |
| **phoneme_description** | ❌ 拟测只是标签（陰去33） | **翻** |

**结果：111 条 × 2 语言 = 222 条。** 没有汉字对照的法语正文 19,771 字；含汉字对照的 44,409 字整体跳过。

> 附带否掉一个看似有效的启发式：用「法语含逗号/括号/词数>2」预筛需要翻译的条目。金标覆盖率仅 18%，
> 随机切片上也漏掉 `泥 ⟨terre⟩`、`犂 ⟨labourer⟩` 这类单词却需要消歧的条目。
> **「需要翻译」的信号不在法语文本的形状里**，只能靠与汉字比对得出。

## 二、两种语言，两套译文

源数据不随界面语言改变（那是学术记录），但译文是**阅读辅助**，语言应跟着读者走：

| 页面 | LLM 列内容 |
|---|---|
| `/introduction`、`/phoneme_description` | 法 → **英** |
| `/yue/…` 同上两页 | 法 → **繁體粵文** |

粵文提示词明确写了「**要写粤文，不是标准书面中文**」并列出替换表（是→係、的→嘅、不→唔、在→喺、看→睇、打雷→行雷…），
同时注明「名詞與專業術語照常寫，不必強行口語化」。

实测（导言首句）：

> 好多見識好高嘅人都話，「粵語」唔係一種語言，只係一種方言。**我哋冇本事**證明「粵語」係一種語言；
> 不過我哋認為，始終可以**當佢係**一種語言：**喺**廣東同廣西兩省…情況**同**安南語**喺**北圻…通行嘅**差唔多**。

是真正的粤语句式，不是「书面语里撒几个嘅字」。

## 三、gold set 基线评测

用 215 条法语人工校订做验收集，同一子集对比：

| Google 翻译（现行） | 18% | 5% |
| **DeepSeek V4.1 Flash** | **44%** | **17%** |

字符串比对低估真实质量，故另派 3 个评审子代理按语义判定（繁简不算错、同义不算错、词典体只要覆盖核心义项即算对）：
**215 条中 214 条 ok，1 条 bad → 准确率 99.5%**。

唯一一条：汉字 芋頭 / 法语 `igname` / 人工「山药，薯蓣」/ LLM「芋頭」—— `igname` 是山药（薯蓣属）不是芋头，属真实语义错误。

Google 的错误则是**系统性义项选择错误**，而汉字列恰好能修正：

### 附录 L 补记：范围再扩到例句与成语（2026-10-12）

## 修订六：译文列两处返工（2026-10-12，用户指出）

### ✗ 错误一：把翻译放在了第一列

初版把 `LLM Trans.` 插在表格最前面（译文优先）。用户指出这是错的：**翻译不能当作最重要的第一列，原文才係主体。**

已改为：`法語原文` → `LLM Trans.` → …（导言页原本就是此顺序，无需改）。

### ✗ 错误二：粤文译文被「对应汉字」列污染（严重）

**现象**：粤文译文读起嚟係 19 世纪嘅讲法，唔係今日通行嘅粤语。用户举了两例：

| 输出 | 应为 |
|---|---|
| 你去**邊處**？ | 你去**邊度**？ |
| 我**喊打理**去**墟**。 | 我叫**工人**去**街市**。 |

**根因**：提示词把 `c`（对应汉字）字段标成「**这是该条目的权威语义，务必据此判断法语的确切含义**」，
并连同 `t`（越南国语字拼写嘅粤语读音）一并喂给模型。结果模型**直接照住 19 世纪嘅重构汉字写**，
而唔係自己去译法语 —— 等于让「重构汉字」当答案，译文变成佢嘅改写。

**实测污染程度**（239 条例句与成语的粤文译文 vs 对应汉字列）：

| | 条数 |
|---|---|
| 与汉字列完全相同 | 10 |
| 高度雷同（>70%） | 12 |
| 确有改写 | 217 |

旧式词渗漏统计：`邊處`×4、`墟`×2、`打理`×2、`喊`×2、`熱頭`×3、`亞`（「阿」的旧写）×10。

> 注意：「确有改写」的 217 条并非安全 —— 好多只係把汉字列嘅词重新排列、补上虚词，语体仍然係 19 世纪嗰套。
> **字符串相似度呢个指标低估咗污染程度**，因为汉字列有空格分隔、译文係连写句子。

**修正**：
1. **输入去掉 `c` 与 `t`**，只留 `fr`（法语）与 `vi`（越南语注，作理解参考）
2. 提示词改为粤文书写，开宗明义「**呢个係翻译，唔係改写**」同「你唔会收到任何中文或汉字参考」
3. 附旧式→现代对照表：邊處→邊度、墟→街市、打理→工人／傭人、喊→叫、亞爸→阿爸、熱頭→太陽、菢蛋→孵蛋，并禁用文言虚词（之、其、乃、亦、且、而）

英文版同样重跑（虽然英文本身无「古今语体」问题，但同为经 `c` 字段生成，方法学上有同样疑虑，一并消除）。

> **教训**：畀模型嘅「参考上下文」会变成佢嘅答案来源。
> 当初畀 `c` 係为咗帮词表消歧（法语多义词拣正确义项），呢个用途成立；
> 但同一做法套到例句上，就变成「照抄答案」。**同一个字段，对不同任务可能係帮助，亦可能係污染。**

### 修订七：粤文语体两次细化（2026-10-12，用户再次指出）

返工版（修订六）解决了「照抄汉字列」，但引入两个新的判断错误。

#### ✗ 错误一：把仍然通行的粤语词当成旧式词

修订六的提示词列了「旧式 → 现代」对照表，其中两条**分类错误**：

| 我列的替换 | 实际 | 后果 |
|---|---|---|
| 熱頭 → 太陽 | **熱頭今日粤语依然通行** | 把粤语词换成了普通话书面词 |
| 百足 → 蜈蚣 | **百足今日粤语依然通行** | 同上 |

**关键区分**：提示词里的「现代化」其实混了两类东西 ——

| 类别 | 例子 | 处理 |
|---|---|---|
| 已被取代的**旧写法** | 邊處、墟、打理（僕人）、喊（＝叫）、亞爸 | **必须改** |
| 仍然通行的**粤语词** | 熱頭、日頭、百足、天光、月光、晏晝、屋企 | **照用，唔好改成普通话词** |

把第二类也「现代化」，等于用普通话语体替换粤语语体，与目标相反。

#### ✗ 错误二：丢失粤语口语词（去掉 `c` 字段的副作用）

用户例：`拔咗雞毛` 应为 **`掹咗雞毛`**。

**这暴露了返工的一个深层矛盾**：去掉 `c`（对应汉字）确实解决了照抄，但也让模型丢掉了粤语特有词汇 ——
恰恰好这些本字（掹、撳、搲、罯、蜎、擻）就係语料库要记录嘅嘢。

| 方案 | 结果 |
|---|---|
| 畀 `c` 字段 | 模型照抄 19 世纪重构（污染） |
| 唔畀 `c` 字段 | 模型退回普通话书面词（丢失粤语词） |

**正解**：唔畀答案，但畀**语体指引** —— 在提示词中列出常用「普通话词 → 粤语词」对照（掹、撳、罯、搲、搣、擻、掟、匿、劏、蜎），
教语体而唔係畀答案。

#### 实测影响范围（返工版 239 条扫描）

| 问题 | 条数 |
|---|---|
| 普通话书面词替换（拔→掹、站→企、找→搵） | 3 |
| 汉字列用到、译文未用的粤语本字（擻、撳、搲、罯、蜎） | 6（其中 4 条汉字列本身 OCR 残破，对不上属正常） |

真正需要修正的约 3–6 条，但根因在提示词，故整体重跑。

> **教训**：「现代化」同「口语化」係两件事。前者係淘汰已死嘅写法，后者係坚持用粤语词汇而唔退向普通话。
> 我第一次把两者混为一谈，结果一边正确改掉 邊處，一边错误地把 熱頭 改成 太陽。

#### 第三版被推翻：全量重跑反而更差

修订七的修正思路是「在提示词加入粤语口语词对照表（掹/撳/罯/搲/搣/擻/掟/匿/劏/蜎）」，然后整批重跑。
结果**语体系统性变书面**，比对成语 45 条：

| 指标 | 第二版（重跑前） | 第三版（加对照表后） |
|---|---|---|
| 书面词种类 | 2 种（盜、尊敬） | **12 种**（搶掠、災禍、恩情、安寧、辛勞、精湛、魂魄、規矩、折磨、逃得過…） |
| 口语词种类 | 7 种（賊、強盜、禍、恩、安樂、辛苦、魂） | 3 种 |

典型对照：

| 法语 | 第二版（更口语） | 第三版（更书面） |
|---|---|---|
| `Grande pauvreté engendre vol et piraterie` | 窮到極就會出賊出強盜 | 窮到極，就會生出偷盜同搶掠 |
| `Se sauver d’une maladie grave…` | 大病醫返好，等於從火裏面走出嚟 | 逃得過一場大病，就等於逃得過一場火災 |
| `Nourrir un tigre…` | 養老虎即係自己攞禍嚟 | 養一隻老虎，即係為自己準備災禍 |

**结论：第三版不采用，保留第二版。** 用户指出的问题实际只涉两处用词，做定点修正即可：

| 条目 | 修正 | 依据 |
|---|---|---|
| 例句 i=21 | 拔咗雞毛 → **掹咗雞毛** | 拔为普通话词，掹为粤语本字 |
| 例句 i=22 | 要去拍吓 → **要去擻吓** | 汉字列作「擻整」，法语 `secouer`（抖开），擻 比 拍 准确 |

（扫描出的其余「书面词」均为误报：`找數` 是正确粤语（结账），`站崗` 亦为通行用法。）

另：第二版**并未丢鹰** —— 成语 i=22 作「一百歲嘅老人家都比唔上一隻成年嘅鷹」，与法语 `l’aigle adulte` 相符。

> **第二次教训**：想修正某个具体用词时，**整批重跑是不可控的** —— 提示词一改，239 条全部重新采样，语体漂移的风险远大于修好那两处的收益。
> 定点修正（2 条）比全量重跑（239 条）更精确、更安全。

#### 第三版「本字修正」多为无据（深入核查）

第三版例句表面上「更准确地用了粤语本字」（搲、匿、企、蜎），逐条对照汉字列后发现**多数係模型自己造嘅，唔係语料本身嘅用字**：

| i | 汉字列实际用字 | 第二版 | 第三版 | 判定 |
|---|---|---|---|---|
| 98 | **扒** | **扒**開啲泥 | 搲地 | 第二版正确，第三版改错 |
| 99 | **撓** | 抓 | 搲 | 两者都偏离，第二版较近 |
| 107 | **藏** | 入山洞**避雨** | 匿入 | 第二版合法语 `s’abriter` |
| 143 | 更編朆（残破） | 站崗 | 企崗 | 汉字列残破，无从判定 |
| **175** | **蜎** | 潛入 | **蜎入屋** | **第三版正确，已定点采纳** |

**第三版地名判定同样不可靠**：

| 原文 | 第三版 | 问题 |
|---|---|---|
| `Hacoi` | 河內 | ✗ 河內係 Hanoi；Hacoi 係河檜 |
| `Tonkin` | 北越 | ✗ 史料术语应为北圻 |
| `Pac Si` | 北泗 | ✗ 音译，语料库应保留原书罗马字 |
| `Ke-Bao` | 計保 | ✗ 同上 |
| `sou`（货币） | 蘇 | ✗ 第二版作「銅錢」较妥 |

**最终决定：保留第二版为底本，只做三处定点修正。**

| 条目 | 修正 | 依据 |
|---|---|---|
| 例句 i=21 | 拔 → **掹** | 粤语本字 |
| 例句 i=22 | 拍吓 → **擻吓** | 汉字列作「擻整」，法语 `secouer` |
| 例句 i=175 | 潛入屋 → **蜎入屋** | 汉字列用「蜎」，法语 `se glisser furtivement` |

> **第三次教训**：模型「看起来更地道」嘅改动，可能係**凭空生成**而唔係忠于语料。
> 判断本字用对无对，唯一可靠依据係汉字列本身，唔係模型嘅语感。
> 三次全量重跑（每轮 239 条）最终换嚟 3 处定点修正 —— 说明呢类细粒度用词问题应该逐条查证，唔应该靠重跑。

## 修订八：外壳三项（主题 / 语言识别 / 移动端顶栏）（2026-10-12）

### 一、主题切换（跟随系统 / 日间 / 夜间）

调色板本来就全是 CSS 自定义属性，所以暗色是**在 `:root[data-theme="dark"]` 覆写变量**，而不是新写一套规则。
用暖调深色（`#14130f` 画布 / `#f4efe6` 墨色），不是中性黑，保住「档案纸」质感。

- `<head>` 内的**同步内联脚本**在首次绘制前定好主题 → 无闪白
- 单按钮循环：跟随系统 → 日间 → 夜间，偏好存 `localStorage`
- 跟随系统时监听 `prefers-color-scheme` 变化，实时反映

**顺带修掉 9 处硬编码颜色**（`#fff` × 6、`#3a3733`、一个面板阴影、主色上的文字色）。
其中 3 处 `#fff` 面板（搜索框、列选择器、表格容器）原本在暗色下会刺眼。

### 二、浏览器语言自动识别

英文页里一段内联脚本，把报告中文的浏览器送到对应的 `/yue/` 路径。匹配 `/^(zh|yue|cmn|nan|hak|lzh)/i`。

- **`/yue/` 页不含这段脚本**（用 `{locale === 'en' && …}` 条件输出），所以不可能循环
- 手动点过语言切换后写 `localStorage`，之后**永不自动跳转**
- 保留路径：`/vocabulary/` → `/yue/vocabulary/`

**9 项测试全部通过**：

| 浏览器语言 | 结果 |
|---|---|
| zh-CN / zh-TW / zh-Hant-HK / yue | → `/yue/…` ✓ |
| en-US / fr-FR / ja-JP | 留在英文站 ✓ |
| 中文，但已手动选过任一种语言 | 不跳转 ✓ |

### 三、移动端顶栏（用户要求「不要缩成几行」）

**根因不是「没做移动端适配」，是顶栏本来就卡在临界点。** 实测（1400px 视口）：

```
wordmark 392 + nav 715 + langbar 76 = 1183，加 2 个 28px 间隙 = 1239
容器宽 1240  ← 只差 1px
```

所以加任何东西都会溢出换行。加上主题按钮后变成 1299 > 1240，按钮被挤到第二行，**顶栏从 53px 涨到 115px**。

**修法不是「再挤一点」，而是永不换行 + 允许收缩：**

- `.masthead .bar` 设 `flex-wrap: nowrap`
- 站点名 `min-width: 0` + 单行截断（超出显示省略号）
- 导航 `min-width: 0` + 内部横向滚动
- 语言切换与主题按钮 `flex: 0 0 auto`（固定尺寸）

| 视口 | 修改前 | 修改后 |
|---|---|---|
| 1400px | 115px（换行） | **53px** |
| 1000px | — | **53px** |
| 700px | — | **53px** |
| 375px | ~100px（三行） | **55px** + 抽屉 |

移动端按优先级重排：站点名收成短名（`app.shortTitle`）、7 项导航进抽屉、语言与主题留在栏上。

### 测试中揪出的两个真 bug

#### ✗ 桌面端导航整个消失（`w=0 h=0`，全站所有宽度）

我用 `<details>` 做抽屉，但**新版 Chromium 用 `content-visibility` 隐藏其内容，`display` 规则覆盖不了它**。
（不是 UA 样式表的 `details:not([open]) > *:not(summary)` 机制，那条确实能被作者样式覆盖。）

改为 `<button>` + `body.nav-open` 类，行为完全可控，并补上 Escape 关闭、点击外部关闭、
`aria-expanded` / `aria-controls`。

#### ✗ 英文站点名换成两行，顶栏涨到 83px 且 About 链接被切断

截断规则写的是 `.wordmark > span:last-child`。加入移动端短名（第二个 span）之后，
**它指向了那个在桌面端隐藏的 span**，全名反而没有 `nowrap`。改成显式命名两个类。

> **教训**：两个都是「加了新东西才暴露」的问题，只读代码看不出来，都是**量出来的**。
> 尤其第一个：导航消失后页面看起来「正常」，只是少了导航——没有测量就发现不了。
